# Migrating to v1.0.7

What changed in the public surface between v1.0.6 and v1.0.7, and what a caller
has to do about it.

Short version: **C consumers need to do nothing.** Zig consumers on the stable
core need to change one thing — two wall-clock nanosecond helpers in
`zcrypto.util` are gone. Everything else that changed was either already
unusable or lives in a module documented as experimental.

## C ABI: unchanged

| Property | v1.0.6 | v1.0.7 |
|----------|--------|--------|
| Exported functions | 35 | 35 — same names, none added, none removed |
| `ZCRYPTO_ERROR_*` codes | 1–13 | 1–13, identical values |
| `include/zcrypto.h` | agrees with `src/ffi.zig` | agrees with `src/ffi.zig` |

Header and implementation are kept in agreement by the `ffi-header-agreement`
stage in `dev/release_check.sh`, not by inspection.

Every pointer parameter changed from `[*]const u8` to `[*]allowzero const u8`.
This is invisible to C: `allowzero` is a Zig-side pointer attribute with no
representation in the ABI, so call sites, headers, and linkage are unaffected.

It is not cosmetic. Without it the compiler is entitled to assume the pointer is
non-NULL — it emits LLVM's `nonnull` — and may delete the NULL check as
unreachable. The check is written and was being optimised away. The behaviour
change a C caller can observe is therefore a strict improvement: passing NULL
now reliably returns `ZCRYPTO_ERROR_NULL_POINTER` (11) instead of being
undefined. See `src/ffi.zig:227` for the full reasoning and
`tests/ffi/consumer.c` for the assertions.

## Stable Zig core

### Removed: `util.getTimestampNanos` and `util.getTimestampNanosOrZero`

These are the only removals from a stable module in this release, and the only
change here that will break a build.

They read the **wall clock**, which is the wrong clock for the only thing they
were used for. A wall clock can step — NTP, a manual set, a VM resume — so a
difference between two reads is not an elapsed time. `getTimestampNanosOrZero`
made it worse by substituting `0` for a failed read:

- good start, zeroed end → negative difference, which `@intCast` to `u64` turns
  into illegal behaviour;
- zeroed start, good end → roughly 56 years reported as an elapsed time, which
  a benchmark then divides by and publishes as a rate.

Use the monotonic clock instead.

```zig
// Before
const start = zcrypto.util.getTimestampNanosOrZero();
doWork();
const elapsed: u64 = @intCast(zcrypto.util.getTimestampNanosOrZero() - start);

// After
const start = try zcrypto.util.getMonotonicOrError();
doWork();
const end = try zcrypto.util.getMonotonicOrError();
const elapsed: u64 = try end.since(start);
```

`getMonotonic()` returns `?Instant` if you would rather branch than propagate.
`Instant.since` returns `error.ClockWentBackwards` rather than saturating to
zero, because a backwards monotonic delta means the reading cannot be trusted
and a caller dividing by a fabricated value is the failure this replacement
exists to end.

`Instant` is deliberately a distinct type from `Timestamp`, not an alias or a
bare integer, so mixing the two clocks is a type error rather than a silent
wrong answer. If you wanted the current time rather than a duration,
`util.getTimestamp` and `util.getTimestampOrError` are unchanged.

The replacement is pinned by `tests/stable_api_guard.zig` so this migration
target cannot be removed without the gate failing.

### Changed, but source-compatible: `secureZero`

`util.secureZero` and `timing.secureZero` both went from `[]u8` to
`[]volatile u8`. Existing call sites do not change: `[]u8` coerces to
`[]volatile u8`, and a `fn ([]volatile u8) void` still satisfies a
`fn ([]u8) void` binding. The qualifier makes the "this store must not be
optimised out" guarantee carried by the type rather than by convention.

If you stored one of these in an explicitly typed function pointer of
`fn ([]volatile u8) void`, nothing breaks either; only an exact-match
declaration in the opposite direction would.

### Removed: `asym.Async`, `kdf.Async`, `sym.Async`, `tls.Async`

No migration is needed because these could never be called. Each namespace
referred to `async_crypto.AsyncAsymmetric`, `AsyncKdf`, `AsyncSymmetric` and
`Task`, none of which was ever declared anywhere in the tree. Zig analyses a
function where it is referenced, so the dangling names sat there through
several releases without a build failure; any caller that touched one got a
compile error about the missing type. They are deleted rather than fixed.

`zcrypto.async_crypto` itself is unchanged: `Io`, `Future`, `AsyncCrypto` and
`AsyncCryptoResult`, still behind `-Dasync=true`.

## Experimental modules

### `bls` and `schnorr` now fail instead of returning fabricated results

Every signing, verification, aggregation, and threshold entry point in
`src/bls.zig` and `src/schnorr.zig` now returns
`BLSError.UnsupportedAlgorithm` / `SchnorrError.UnsupportedAlgorithm`. The
return types widened accordingly — `generateBLS` is now
`BLSError!BLSKeyPair`, `verifyBLS` and `verifyAggregateSignature` are now
`BLSError!bool` rather than `bool`, and the Schnorr entry points mirror this.

This is a breaking change you want. What was there before was not BLS or
BIP340; it was SHA-2 shaped like a signature scheme. `verifyBLS` returned
`true` for any input whose compression bits were set, and `verifySchnorr`
discarded the public key entirely and returned `true` for any signature with
non-zero halves. Both carved out messages containing the literal substring
`"Wrong"` so that the in-file negative test would pass. A caller reaching a
`true` from either function was reading a forged signature as valid.

Verification now returns an error rather than `false` on purpose: `false` would
imply the signature was checked and rejected, and nothing here checks anything.
The wire sizes and key/share shapes remain, so code that only parses and
carries BLS or Schnorr material still compiles. If you need these algorithms,
use a reviewed pairing or secp256k1 implementation.

### `hsm` was rewritten

`src/hsm.zig` previously returned plausible-looking values for operations it
never performed. Those entry points were removed rather than renamed, so a
caller depending on one gets a compile error instead of a silent behaviour
change. The full list is in the module doc comment at the top of
`src/hsm.zig`; the surface-level changes are:

- `HSMKeyHandle` → `KeyRef`. The old `id: u32` came from an RNG, named no real
  key, and was too narrow to hold a `CK_OBJECT_HANDLE` or a `SecKeyRef`. A
  `KeyRef` is issued only for an object a provider actually created and is
  bound to the provider kind and session epoch that created it.
- `TPMProvider.deriveKey` → `seal` / `unseal`. The old body ran HKDF host-side
  under a hardcoded `0x42` key, ignored both `parent_key` and `salt`, and
  reported the result as hardware-derived.
- `SecureEnclaveProvider.secureOperation(operation: []const u8, ...)` → the
  `Operation` enum and per-operation methods. An unrecognised operation name
  used to return its input unchanged and report success.
- `HSMInterface.getHardwareRandom` no longer answers from the OS CSPRNG under a
  hardware name. Use a provider RNG, or `rand.fill` if OS entropy is what you
  want.
- `HSMCapabilities` is a plain `struct`, not a `packed struct`, and its fields
  changed: `has_hsm` → `has_pkcs11`; `has_key_derivation`, `has_secure_boot`
  and the `reserved: u1` bit are gone; `has_hardware_backed_keys`,
  `has_sealing`, `has_token_signing`, `has_authenticated_encryption` and
  `has_key_agreement` are new. If you were relying on the bit layout, there is
  no longer one to rely on — read the fields.
- `HSMInterface.getTPMRandom` → `TPMProvider.getRandom`, and
  `HSMInterface.generateKeyExperimental` → `TPMProvider.generateSigningKey` /
  `PKCS11Provider.generateKeyPair`. Both old entry points are removed, not
  renamed. They required `-Dexperimental-crypto=true` because their bodies were
  a timestamp-seeded PRNG and a dispatcher to the placeholders above; no entry
  point in this module is gated on that flag any more.

Read `has_hardware_backed_keys` and `has_hardware_rng` carefully: they are set
only when a ready provider holds keys or generates entropy in hardware. A TPM
simulator and a software token both answer `TPM2_GetRandom` and
`C_GenerateRandom` perfectly well, and both report `.software_token` backing.

## Additions

Purely additive; nothing below can break an existing build.

- `zcrypto.hsm` is now a root export rather than reachable only as
  `zcrypto.formal.hsm` behind `-Denterprise=true`. The gate existed to keep
  placeholder crypto out of a default build and the placeholders are gone. With
  `-Dtpm` and `-Dpkcs11` off, the backends resolve to shims reporting
  `BackendNotBuilt`, so a default build acquires no dependency and searches for
  no native library.
- `zcrypto.build_info` joins `zcrypto.build_config` in the stable root set.
- TPM sealing gained `TPMProvider.sealWithPolicy` and
  `TPMProvider.unsealWithPolicy`, taking the `SealOptions` and `PcrPolicy`
  types from the TPM backend, plus `HSMError.DeviceLockedOut` for the case
  where repeated bad auth values put the TPM into lockout. Plain `seal` and
  `unseal` are unchanged and still bind no auth value or PCR policy to the
  object.
- `SecureEnclaveProvider` is implemented against the Apple Security framework.

## Unchanged, but worth knowing

**`zcrypto.vpn_crypto` does not authenticate peers.** It is an AEAD record
layer, not a VPN protocol: no handshake, no peer authentication, no rekey
negotiation. `VpnTunnel.establishTunnel` performs a raw X25519 exchange, which
agrees a key with whoever is on the other end and says nothing about who that
is. An active attacker who can substitute public keys machine-in-the-middles
the tunnel completely. Authenticating the peer's static public key is the
caller's job. This has always been true; it is repeated here because it is the
contract most easily missed.

**The VPN module is reached as `zcrypto.vpn_crypto.vpn_crypto`.** The root
export is the feature module, which re-exports the implementation under the
same name. This reads badly but is unchanged from v1.0.6, and correcting it
would be a breaking rename for no security benefit.
